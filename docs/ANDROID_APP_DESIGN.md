## 1. Purpose and scope

This document analyses the existing Gold Loan Tracker web application and specifies a native Android application that gives the same business the ability to manage customers, pledged gold ornaments, bank loan limits, loans, payments and releases from a phone.

It covers product goals, users, information architecture, screen-level specifications, backend and API changes, data and sync design, security, non-functional requirements and a phased delivery plan. It does not contain final visual designs; it defines the design system and the per-screen behaviour those designs must follow.

## 2. Analysis of the current web application

### 2.1 Architecture as built

```
Browser (index.html: Tailwind CSS, SweetAlert2, vanilla JS)
   │  google.script.run.<functionName>(...)   ← RPC bridge, only works inside the served page
   ▼
Google Apps Script (code.js) — executes as the sheet owner, "Anyone" may open the web app
   ├── Google Sheets  — 8 tabs used as tables
   ├── Google Drive   — "GoldLoanApp_Uploads/{Customer_Photos,Passbook_Images,Ornament_Images,Delivery_Proofs}"
   ├── CacheService   — 30 minute cache of scraped gold rates
   └── PropertiesService — last-known-good gold rates
```

The front-end domain `goldloan.brewflock.com` embeds the Apps Script `/exec` URL in an iframe.

### 2.4 Business rules that must be preserved

These are documented in `CALCULATIONS.md` and verified in code.

1. **Net disbursement** = Loan amount − (processing fee + document charge + insurance charge). Interest is never deducted up front.
2. **Total charges** = interest for the loan period + processing fee. Reporting figure only.
3. **Interest period in months** = LoanPeriod if set, otherwise round((DueDate − LoanDate) / 30.4375 days), minimum 1.
4. **Simple interest** = P × R/100 × months/12. **Compound interest** (monthly) = P × (1 + R/1200)^months − P. Both rounded to 2 decimals.
5. **Bank utilization** = sum of LoanAmount over that customer's Active loans on that account. **Available** = max(0, Max − Utilized). A new or edited active loan may not exceed Available.
6. **Ornament gold weight** = MetalWeight, else NetWeight, else max(0, Gross − Stone).
7. **Current gold value** = live 22K rate × total gold weight (24K rate as fallback). **Buying value** = Σ(buying rate × weight) or TotalPrice. **Appreciation** = current − buying.
8. **Closing a loan** marks the loan Closed, marks its LoanOrnaments mappings Released, marks each ornament Released with ReleaseDate and ReleasedLoanId, and re-syncs bank utilization.
9. **Editing an active loan's ornament set** deletes removed mappings and returns those ornaments to Available; added ornaments become Pledged.
10. A loan number must be unique among loans that are not Cancelled.

### 2.5 Gaps and defects found during analysis

These shape the mobile scope and the backend work that must precede it.

| # | Finding | Impact on mobile design |
|---|---|---|
| G1 | `addPayment` and `releaseOrnaments` exist in the backend but **no screen calls them**. Payments can only be entered by editing the sheet. | Record Payment is a first-class mobile screen. |
| G2 | **No outstanding balance** is computed anywhere. Payments are listed and summed but never netted against principal or interest. | Define the balance formula (section 8.3) and show it on loan cards. |
| G3 | The backend has **no authentication on data calls**. Any client that can reach the web app can call any function. Passwords are plain text. | Phase 0 must add a token-based JSON API and hashed passwords before a public-store app ships. |
| G4 | The web app relies on `google.script.run`, which is **not reachable from a native app**. | A `doPost` JSON router is required (section 7). |
| G5 | `closeAndReleaseLoan` sets ornaments to `Released`, but `releaseOrnaments` sets them to `Available`. `Released` ornaments are still offered for new pledges. | Mobile treats Released as re-pledgeable and shows it as a distinct chip. Unify on the backend. |
| G6 | ID generation reads the whole sheet and is not atomic. Two concurrent writes can collide. | Backend wraps writes in `LockService`; client sends an idempotency key per write. |
| G7 | Drive uploads are shared as "anyone with the link". Customer KYC photos and passbooks are therefore publicly reachable by URL. | Mobile fetches images through an authenticated proxy endpoint; sharing tightened in Phase 0. |
| G8 | Due date is typed manually and is not derived from LoanDate + LoanPeriod, so the two can drift. | Mobile auto-fills DueDate from period and warns when they disagree. |
| G9 | `Cancelled` is referenced in duplicate checks but nothing can set it. | Add a Cancel Loan action with reason, restricted to loans with no payments. |
| G10 | Chart.js is loaded but never used. Theme choice is not persisted. | Mobile persists theme in DataStore. Charts deferred to Phase 3. |
| G11 | Every list call returns the full sheet. With thousands of rows, each screen open becomes a multi-second call. | Mobile caches in Room and uses delta sync by `UpdatedDate` (section 8.4). |
| G12 | No audit trail of who did what, and only one role (SuperAdmin) is meaningful. | Backend logs `actor` on every write from Phase 0. Roles in Phase 3. |

## 3. Product vision and goals

**Vision.** The operator of a small gold loan business can run the entire pledge lifecycle from a phone at the counter: photograph the ornament, register the customer, book the loan against the right bank limit, collect payments, and hand the jewellery back with proof, all in under a minute per step and without a laptop.

### 3.1 Goals

1. Full parity with the web app for the six existing areas, plus payments and releases that the backend already supports.
2. Faster data entry than the web app through the camera, contact picker, barcode-free auto-derivation of weights and charges, and sensible defaults.
3. Reliable on poor connectivity: every list and detail screen renders from local cache, and writes queue when offline.
4. Safer than the web app: authenticated API, hashed passwords, biometric lock, masked KYC data.
5. A foundation that can later leave Google Sheets without rewriting the app.

### 3.2 Non-goals for version 1

- Customer-facing app or customer self-service.
- Payment gateway or UPI collection inside the app.
- Multi-branch or multi-tenant support.
- iOS. The architecture should not preclude Kotlin Multiplatform later, but no iOS work is planned.
- Replacing Google Sheets as the system of record.

### 3.3 Success metrics

| Metric | Target after 3 months |
|---|---|
| Share of loans created on mobile versus web | ≥ 70 % |
| Median time to create a loan (customer already exists) | ≤ 90 seconds |
| Payments recorded through the app (versus edited in the sheet) | ≥ 95 % |
| Crash-free sessions | ≥ 99.5 % |
| Cold start to interactive dashboard on cached data | ≤ 1.5 seconds |

## 4. Users and journeys

### 4.1 Personas

| Persona | Description | Primary needs |
|---|---|---|
| **Owner-operator** (primary) | Runs the business, is the only SuperAdmin today, works at the counter and on the move. | See exposure and gold value at a glance. Book loans quickly. Never lose a payment record. |
| **Counter staff** (Phase 3) | Registers customers and ornaments, records payments. Should not close loans or change bank limits. | Simple guided forms, no access to financial settings. |
| **Accountant / auditor** (read-only, Phase 3) | Reviews loans and payments monthly. | Filters, exports, no editing. |

### 4.2 Core journeys

1. **New pledge, new customer.** Dashboard → Loans → New Loan → "Add customer" inline (name, mobile from contacts, photo from camera) → add bank account or pick existing → add ornaments with camera and weights → terms → review charges → confirm. Ornaments become Pledged, bank utilization updates.
2. **Collect a payment.** Search customer or loan number → Loan detail → Record Payment → amount, type, method, reference → save. Balance updates on the card.
3. **Close and release.** Loan detail → Close & Release → confirm remaining balance is zero (or override with remark) → capture delivery photo and customer signature → done. Ornaments become Released.
4. **Morning check.** Open app → Dashboard shows today's gold rates, loans due this week, overdue loans, current gold value versus buying value.
5. **Look up an ornament.** Ornaments → filter Pledged → tap → see photos, weights, which loan it is on, and the customer.

## 5. Architecture

### 5.1 Options considered

| Option | Description | Verdict |
|---|---|---|
| A. Keep Apps Script, add JSON API | Add `doPost` router, token auth, hashing, locking to `code.js`. Sheets stay the source of truth. | **Recommended for Phase 0–2.** Lowest cost, keeps the web app working, no data migration. |
| B. Firebase (Auth + Firestore + Storage) | Rewrite backend, migrate data. | Better long term, but doubles Phase 1 scope. Revisit in Phase 3 once the app proves value. |
| C. WebView wrapper around the current web app | Ship the existing UI in a WebView. | Rejected. No offline, no camera integration, inherits every gap in section 2.5, and the RPC bridge is fragile in WebView. |

The app isolates all server access behind repository interfaces so that a move from A to B changes only the data layer.

### 5.2 System diagram (target state)

```
Android app (Kotlin, Jetpack Compose)
 ├── UI layer: Compose screens + ViewModels (MVVM, unidirectional data flow)
 ├── Domain layer: use cases, LoanCalculator, validation rules (pure Kotlin, unit tested)
 ├── Data layer: Repositories
 │     ├── Local: Room database (cache + outbox), DataStore (prefs), EncryptedSharedPreferences (token)
 │     └── Remote: Retrofit + OkHttp → Apps Script JSON API
 └── Background: WorkManager (sync, outbox flush, due-date reminders)

Apps Script (code.js)
 ├── doPost(e): JSON router {action, token, requestId, payload}
 ├── Auth: login → session token (CacheService, 12 h TTL), passwords hashed (SHA-256 + per-user salt)
 ├── Existing functions reused unchanged behind the router
 ├── LockService around every write; requestId de-duplication
 └── /image?id= proxy that streams Drive files to authenticated callers
```

### 5.3 Technology stack

| Concern | Choice | Reason |
|---|---|---|
| Language | Kotlin 2.x | Standard for Android. |
| UI | Jetpack Compose, Material 3 | Declarative, dynamic colour, adaptive layouts for tablets. |
| Architecture | MVVM + Clean layers, single-activity, Compose Navigation | Testable, matches Android guidance. |
| DI | Hilt | |

## 7. Backend and API changes (Phase 0 prerequisite)

### 7.1 Request envelope

All calls are `POST {execUrl}` with `Content-Type: text/plain` (avoids a preflight for the web client) and a JSON body:

```json
{
  "action": "loans.create",
  "token": "<session token>",
  "requestId": "3c4e…-uuid",
  "clientVersion": "android/1.0.0 (42)",
  "payload": { }
}
```

Response envelope is the existing `{ success, data, error }` plus `serverTime` and, on auth failure, `code: "UNAUTHORIZED"` so the app can log out.

### 7.2 Action map

| Action | Existing function | Notes |
|---|---|---|
| `auth.login` | `authenticateAdmin` | Returns `{ token, username, role, expiresAt }`. Compares hashed password. |
| `auth.logout` | new | Removes token from cache. |
| `auth.changePassword` | new | Required before Phase 1 goes to store. |
| `dashboard.get` | `getDashboardData` | Add `dueThisWeek`, `overdue` counts and lists. |
| `goldRates.get` | `getGoldRates` | Unchanged. |
| `users.list` / `users.create` / `users.update` / `users.delete` | `getUsers`, `addUser`, `updateUser`, `deleteUser` | `list` accepts `updatedSince` for delta sync. |
| `bankAccounts.list` / `.create` / `.update` / `.delete` | existing | `list` returns `AvailableLoanAmount` as today. |
| `ornaments.list` / `.available` / `.create` / `.update` / `.delete` / `.deleteImage` | existing | `list` accepts `updatedSince`; sheet gains `UpdatedDate`. |
| `loans.list` / `.get` / `.create` / `.update` / `.close` / `.cancel` / `.forClosure` | existing plus `cancelLoan` (new) | `close` accepts optional `proofFile` and `signatureFile` and writes Releases rows (merges `releaseOrnaments`). |
| `payments.create` / `payments.listByLoan` | `addPayment`, subset of `getLoanDetails` | New list action so payments can sync independently. |
| `files.get` | new `doGet(e)` branch: `?image=<fileId>&token=` | Streams Drive bytes to authenticated callers so Drive sharing can be set back to private. |

### 7.3 Hardening included in Phase 0

1. Passwords: store `SHA-256(salt + password)` with a per-admin salt column; migrate the seeded admin on first run and force a change.
2. Tokens: random 32-byte value in `CacheService` keyed by token, 12 hour TTL, refreshed on use.
3. Concurrency: `LockService.getScriptLock().waitLock(10000)` around every write; `requestId` stored for 24 hours in cache so a retried write returns the original result instead of creating a duplicate row.
4. Add `UpdatedDate` to Ornaments and LoanOrnaments; set it on every write across all sheets.
5. Add `actor` (username) and `AuditLog` sheet: timestamp, actor, action, entity id, summary.
6. Server-side recomputation of TotalCharges and NetDisbursement on loan create and update, rejecting requests whose client values differ by more than ₹1. This closes the "client sends whatever it likes" gap noted in `CALCULATIONS.md`.
7. Unify release semantics: closing a loan creates Releases rows and sets ornaments to `Released`; `Released` remains pledgeable.

The web app keeps working throughout because `google.script.run` still calls the same underlying functions.

## 8. Data, calculation and sync design

### 8.1 Local schema (Room)

One entity per sheet with the same column names, plus:

- `syncState` on every row: `SYNCED`, `PENDING_CREATE`, `PENDING_UPDATE`, `PENDING_DELETE`, `CONFLICT`.
- `localId` (UUID) for rows created offline before the server assigns `U001`-style ids.
- `Outbox` table: `requestId`, `action`, `payloadJson`, `createdAt`, `attempts`, `lastError`.
- `ImageCache` table mapping Drive file id to local file path.
- `SyncMeta` table: last successful `updatedSince` watermark per entity.

### 8.2 Shared calculator

`LoanCalculator` (pure Kotlin, in the domain module) implements rules 1–7 from section 2.4 exactly, with unit tests that pin the numbers from `CALCULATIONS.md`. It uses `BigDecimal` with `HALF_UP` to 2 places so mobile and web agree to the paisa. The same tests are ported to Apps Script for the server-side check in section 7.3.

### 8.3 New derived figures

These do not exist in the web app and are labelled as **new** so reviewers can approve the definitions.

| Figure | Definition |
|---|---|
| **Total interest due** | From rule 4 for the full loan period. |
| **Total payable** | Loan amount + total interest due + Σ penalty amounts recorded. |
| **Paid so far** | Σ TotalPaidAmount over the loan's payments. |
| **Outstanding balance** | Total payable − paid so far, floored at 0. |
| **Days to due / days overdue** | DueDate − today, in the device's local date. |

Closing a loan with outstanding balance > 0 requires a closure remark and shows a warning. This is a soft check to match the current one-tap behaviour, not a hard block.

### 8.4 Sync strategy

- **Reads are offline-first.** Screens render from Room immediately, then a background refresh calls `*.list` with `updatedSince` and upserts. Pull-to-refresh forces a full fetch.
- **Writes are online-first with an outbox fallback.** If the call succeeds, Room is updated from the response. If the device is offline or the call times out, the row is saved as `PENDING_*`, the request goes to the outbox, and WorkManager retries with exponential backoff up to 24 hours. Pending rows show a small cloud-off icon.
- **Ordering.** The outbox is flushed strictly in creation order so a customer created offline is sent before the loan that references its `localId`. The server response maps `localId` to the real id and the app rewrites references.
- **Conflicts.** The server wins. If an update targets a row whose `UpdatedDate` is newer than the value the client last saw, the server rejects with `CONFLICT`; the app marks the row, keeps the user's values in a "your unsaved changes" sheet and lets them reapply.
- **What never queues offline.** Loan create, loan close and payment create require connectivity in version 1, because bank-limit checks and balance checks must run against current server data. The form explains this and offers to save a draft instead.

### 8.5 Images

- Capture with CameraX or pick from gallery. Compress to a maximum edge of 1280 px, JPEG quality 80, EXIF orientation applied, EXIF location stripped.
- Upload as base64 inside the write payload (current backend contract). Multiple ornament images upload in one request, capped at 5 per request.
- Display through `files.get` with the auth token in a header, cached on disk by Coil and in `ImageCache`.

## 9. Screen specifications

Each screen lists purpose, content, actions, states and validation. Field lists mirror the web forms so that both clients write identical rows.

### 9.1 Login

- Fields: server URL (pre-filled with the production `/exec` URL, editable under an "Advanced" expander), username, password.
- Actions: Sign in. After first successful login, offer "Unlock with fingerprint or face next time".
- States: loading, invalid credentials, server unreachable (with retry and cached-data hint), forced password change when the server flags a default password.
- Session persists until logout or token expiry; app lock with biometric after 5 minutes in the background (configurable).

### 9.2 Dashboard

Ordered top to bottom for a phone:

1. **Gold rate strip**: 22K per gram prominent, 24K and 18K smaller, daily change badge coloured up or down, "Bangalore · updated 09:14" caption, tap to open Gold rates. Warning chip when data is cached or fallback.
2. **Attention cards** (new): "3 loans overdue" and "5 due this week", each tapping into the Loans tab with that filter.
3. **Exposure cards**: Active loan amount, Total eligible limit, Available limit (with a progress bar utilized/eligible).
4. **Gold valuation cards**: Current gold value, Buying gold value, Appreciation with percentage and colour rule from the web app (green positive, red negative, grey zero).
5. **Portfolio counts**: customers, bank accounts, ornaments, pledged ornaments with grams, active loans, closed loans.
6. **Recent payments** (last 5) with loan number and customer.

Pull-to-refresh refreshes dashboard and gold rates. Data timestamp shown at the bottom.

### 9.3 Customers list and detail

- List: photo avatar, name, mobile, customer code, status chip. Search by name, mobile, code. Sort by name or created date. FAB "Add customer".
- Detail header: photo, name, mobile with call and WhatsApp shortcuts, city. Tabs: **Profile** (all KYC fields, Aadhaar and PAN masked with tap-to-reveal), **Bank accounts** (cards with max, utilized, available and a limit bar, FAB add), **Ornaments** (grid of thumbnails with status chips), **Loans** (cards with number, amount, due date, balance, status).
- Overflow: Edit, Deactivate (soft delete after confirmation), Share vCard.

### 9.4 Customer form

Same fields as the web form: Full name*, Father/Husband name, Customer code, Mobile*, Alternate mobile, Email, DOB, Gender, Occupation, Aadhaar, PAN, Address 1, Address 2, City, State, Pincode, Status, Photo.

Mobile-specific behaviour: pick mobile from Contacts; DOB via date picker; Aadhaar formatted as 4-4-4 and validated with the Verhoeff checksum (warning only); PAN validated by pattern; photo via camera with a face-friendly square crop; Pincode lookup to prefill city and state is Phase 3.

### 9.5 Bank account form

Fields: Customer* (locked when opened from a customer), Holder name* (defaults to customer name), Account number*, Bank name*, Branch, City (defaults to customer's city), IFSC (uppercase, pattern check), Account type, UPI ID, Max loan amount, Utilized (read-only, derived), Available (read-only), Status, Passbook image.

### 9.6 Ornaments list and detail

- List: thumbnail, name, type, gross and net grams, purity chip, status chip (Available green, Pledged amber, Released blue), owner name. Filters by status and owner. Search by name, hallmark, id.
- Detail: swipeable gallery, weights block (gross, stone, metal, net), purity, hallmark, quantity, maker, buying rate and total price, estimated and market value, **live value today** = gold weight × live 22K rate (new, derived on device), status, pledge history (loan numbers with dates from LoanOrnaments and Releases).
- Actions: Edit, Add photos, Delete photo, Deactivate. If Pledged, "Open loan" shortcut.

### 9.7 Ornament form

Fields as the web form: Owner, Name*, Type, Category, Quantity, Gross wt*, Stone wt, Metal wt, Net wt, Purity (default 22K), Hallmark, Buying price/g, Total price, Maker, Estimated value, Market value, Description, Remarks, Status, Images.

Auto-derivation matches the web: metal = gross − stone when metal is blank; net mirrors metal; total price = metal × buying rate when total is blank; estimated value defaults to total price. Numeric keypad with three decimals for grams. Camera button captures multiple photos in sequence.

### 9.8 Loans list and detail

- List cards: loan number, customer, bank name, amount, due date, status chip (Active, Overdue in red, Closed, Cancelled), outstanding balance (new), ornament count. Filters: All, Active, Due this week, Overdue, Closed. Search by loan number, customer, mobile.
- Detail sections: **Summary** (amount, net disbursed, interest rate and type, period, due date with days-to-due, total interest, total charges, total payable, paid so far, outstanding); **Bank account** (bank, account, holder, IFSC); **Pledged ornaments** (thumbnails with gross, net, purity, hallmark, estimated value); **Payments** (list with date, type, split, method, reference; total paid); **Closure** (closed date, remarks, delivery proof, signature) when closed.
- Primary actions by status: Active → Record payment, Close & release, Edit, Cancel. Closed → view only, share statement (PDF, Phase 3).

### 9.9 New loan flow (5 steps)

1. **Customer**: search or add inline. Shows the customer's available limit across accounts.
2. **Bank account**: cards for that customer's accounts with available limit; disabled when Available is 0; inline "Add account".
3. **Ornaments**: checklist of Available and Released ornaments, that customer's first, others grouped under "Other owners" (web allows cross-owner pledging; keep it but require a confirmation). Gross and net totals update live and prefill the loan's weight fields; manual override allowed.
4. **Terms**: Loan number* (suggest next number as `LN-YYYYMM-NNN`, editable), Loan date* (today), Period in months, Due date* (auto = loan date + period, editable, warning if it disagrees with period), Amount*, Interest rate*, Interest type, Processing fee, Document charge, Insurance charge, Remarks.
5. **Review**: computed interest, total charges, net disbursement, limit check result, ornament list. Confirm creates the loan. Server error text (for example the limit message) is shown verbatim in a banner as the web does.

Validation follows `submitLoan`: all starred fields, at least one ornament, amount within available limit (client check, server re-checks).

### 9.10 Record payment (new screen)

Fields: Payment date* (today), Payment type (EMI, Partial, Interest only, Full settlement, Penalty), Principal, Interest, Penalty, Total paid* (auto-sum of the three when they are filled, otherwise typed directly), Method (Cash, UPI, Bank transfer, Cheque, Card), Transaction reference, Remarks.

Shows outstanding before and after. "Full settlement" prefills Total with the outstanding balance. On save, offers "Close & release now" when the balance reaches zero.

### 9.11 Close and release

Sheet with: outstanding balance (warning if above zero), closure remarks (required when balance above zero), released-by name (defaults to logged-in user), delivery proof photo (camera), customer signature pad (captured as PNG, stored via the Releases `CustomerSignature` column that exists but is unused today), ornament list with checkboxes all selected. Confirm closes the loan, writes Releases rows, marks ornaments Released and refreshes bank utilization. Success screen offers "Share receipt" (Phase 3).

### 9.12 Gold rates

Full-screen version of the dashboard strip: 24K, 22K, 18K per gram with change badges, source and time, manual refresh, "rates are cached for 30 minutes" note, and a calculator: enter grams and purity to see value at today's rate.

### 9.13 Settings

Theme (System, Light, Dark), biometric lock and timeout, server URL, sync now and last sync time, clear image cache, change password, about and version, logout.

## 10. Design system

- **Colour**: Material 3 dynamic colour disabled in favour of the brand. Primary seed `#EAB308` (the web's brand-500), with the web's scale `#FEFCE8` to `#713F12` mapped to Material tonal roles. Dark surfaces `#0F172A` / `#1E293B` / `#334155` from the web's dark palette. Semantic: success `#10B981`, danger `#EF4444`, warning `#F59E0B`, pledged amber, released blue `#3B82F6`.
- **Typography**: Inter (bundled) mirroring the web. Display for currency figures, tabular numerals enabled so columns align.
- **Formatting**: currency `₹12,34,567` using `en-IN` grouping; grams to 3 decimals with a `g` suffix; dates `dd-MM-yyyy` as the web; relative dates ("due in 4 days", "12 days overdue") on cards.
- **Status chips**: identical wording and colours to the web so users switching between clients see the same meaning.
- **Components**: Material 3 top app bar, bottom navigation, FAB, filter chips, list cards, bottom sheets for quick actions, full-screen dialogs for forms on phones and side sheets on tablets.
- **Adaptive layout**: on widths ≥ 840 dp use a navigation rail and list-detail panes for Customers, Loans and Ornaments.
- **Motion**: shared-element transition from list thumbnail to detail gallery; otherwise Material defaults.
- **Accessibility**: minimum 48 dp targets, content descriptions on all icons, contrast ≥ 4.5:1, TalkBack labels for currency and status chips, large-font layouts verified at 200 %.
- **Localisation**: English first, all strings in resources; Kannada and Hindi planned for Phase 3. Numbers and dates always via locale-aware formatters.

## 12. Security and privacy

| Area | Requirement |
|---|---|
| Transport | HTTPS only, certificate validation on, no cleartext permitted in the network security config. |
| Credentials | Session token in EncryptedSharedPreferences. Password never stored. Biometric unlock guards the app, not the server. |
| KYC data | Aadhaar and PAN masked by default; `FLAG_SECURE` on customer profile, bank account and form screens to block screenshots and recents thumbnails. Room database encrypted with SQLCipher in Phase 2. |
| Images | Fetched through the authenticated proxy; Drive sharing tightened to private in Phase 0. Disk cache lives in app-private storage and is cleared on logout. |
| Server | Hashed passwords, token TTL, lock-protected writes, audit log, verbatim error text limited to the messages the web already shows. |
| Play policy | Camera and Contacts permissions requested in context with rationale. No location or SMS permissions. Data safety form lists KYC collection and its purpose. |
| Backup | Android auto-backup excluded for the database and token so KYC does not land in Google Drive backups unencrypted. |

## 15. Open questions

1. **Outstanding balance rule.** Section 8.3 proposes total payable = amount + full-period interest + penalties. Should interest instead accrue monthly to the current date, so early closure charges less? This changes the closure warning and needs the owner's decision.
2. **Cross-owner pledging.** The web lets a loan for customer A pledge an ornament owned by customer B. Keep, or restrict to the loan's customer?
3. **Released versus Available.** Should a released ornament return to Available automatically, or stay Released until an operator confirms it is back in stock?
4. **Loan number format.** Is there an existing numbering convention from the bank paperwork that the suggested `LN-YYYYMM-NNN` should follow instead?
5. **Gold rate city.** Rates are Bangalore-only today. Is a city setting needed?
6. **Store distribution.** Public Play Store listing, or private distribution via Managed Google Play or an internal testing track only? This affects Play policy work in section 12.
7. **Multi-device.** Will more than one phone use the app at once in Phase 1? If yes, conflict handling in section 8.4 must ship in Phase 1 rather than Phase 2.
